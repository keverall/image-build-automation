# The client workflow is now reduced to **one setup command**.

## Run once on the client server:

```powershell
make setup
```

`make setup` now automatically:

1. Installs/uses the bundled offline modules.
2. Adds `scripts/modules` to the current `PSModulePath`.
3. Persists that module path for future PowerShell sessions.
4. Imports `HPEOneView.1000`.
5. Verifies `Get-OVServer` and `Get-OVIloSso`.
6. Configures the PowerShell profile.

After that, the operator only runs the build command:

```powershell
Configure-PhysicalBuild `
    -ServerIdentifier 'CZ22420JCN' `
    -OneViewHost 'va-oneviewt-01' `
    -ExternalIsoPath 'Y:\WIN2019Auto.iso' `
    -GuardRail 'qlikview-03ilo'
```

No manual `Import-Module`, `Get-Command`, `Get-OVServer`, or SSO verification commands are required.

The only expected manual interaction during the build is the destructive approval:

```text
APPROVE
```

The SSO parameter correction is included in the repository, so `make setup` loads the correct offline HPE module and the automation uses:

```powershell
Get-OVIloSso -IloRestSession
```

not the invalid `-IloSsoSession` parameter.


## Fixed. The bundled HPE OneView module uses:

```powershell
Get-OVIloSso -IloRestSession
```

It does **not** use:

```powershell
-IloSsoSession
```

The previous code used the wrong parameter name, causing:

```text
A parameter cannot be found that matches parameter name 'IloSsoSession'
```

I corrected:

```powershell
Get-OVServer -Name $OneViewServerName |
    Get-OVIloSso -IloRestSession
```

I also corrected the SSO object handling. The bundled module returns:

```text
RootUri
X-Auth-Token
```

The Redfish session previously looked for a nonexistent `Token` property and incorrectly appended `/redfish/v1` to the already complete `RootUri`. It now uses:

```powershell
$SsoSession.RootUri
$SsoSession.'X-Auth-Token'
```

and preserves the returned Redfish endpoint.

The offline setup continues to be automated with:

```powershell
make setup
```
