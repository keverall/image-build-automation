**Standard:** EU EMIR (Reg. 648/2012) Art. 34 operational risk; DORA (Reg.
2022/2554) Art. 8–10 ICT risk management; EBA Guidelines on ICT and security
risk management (EBA/GL/2019/04).

**Scope of this document:** the GitLab CI/CD pipeline and the CI gates that
protect changes to the automation that touches production banking
infrastructure. It treats the pipeline itself as an in-scope ICT system.

## 1. What the pipeline now does

| Stage | Job(s) | Control | Tier required |
|-------|--------|---------|---------------|
| bootstrap | `cyberark-bootstrap` | Retrieve runtime secrets from CyberArk (no secrets in repo) | any |
| validate | `validate-pipeline`, `validate-config` | Fail fast on broken pipeline / config | any |
| lint | `lint-powershell` | Parsing + PSScriptAnalyzer *style* rules | any |
| test | `test-unit` | Pester with Cobertura + JUnit, coverage measured vs 70% | any |
| security | `sast-powershell`, `secret_detection`, `semgrep-sast`, `iac-sast`, dependency + container scanning | Find injection, insecure creds, secrets, IaC/dep CVEs | SD: Free; rest Free/Ultimate |
| compliance | `compliance-evidence` | Single retained record of which controls ran | any |
| maintenance | `maintenance-*` | Production change jobs (manual / trigger only) | any |

**Critical fact about GitLab SAST on this repository:** GitLab ships **no
PowerShell SAST analyzer**. The Semgrep-based `semgrep-sast` job covers the
Python helper (`scripts/MD_to_HTML_Converter.py`) and any IaC, but it does
**not** scan PowerShell. All ~20,000 lines of PowerShell are scanned *only* by
the `sast-powershell` job (PSScriptAnalyzer security ruleset). If that job is
removed, the PowerShell is entirely unscanned. This is the single most
important thing for a reviewer to understand.

Secret Detection (Gitleaks) **is** available on all tiers and runs a
**historic** scan, so it catches credentials committed and later "removed".

## 2. Remediation posture (report-only → enforce)

The repository has known, real security findings today (see §4). Turning the
gate to `enforce` immediately would make the pipeline red on every commit. To
keep work flowing while the backlog is triaged, the gate runs in **report** mode:

```yaml
variables:
  SECURITY_ENFORCEMENT_MODE: "report"   # report | enforce
  SECURITY_FAIL_ON: "Warning"
```

- In `report` mode, findings are published to the MR (Code Quality widget) and,
  on Ultimate, the Security Dashboard, but the job does not fail the pipeline.
- The **cutover to `enforce`** requires:
  1. Product/AppSec review of every entry in `.security-baseline.json`
     (owner, justification, expiry set — currently `UNASSIGNED`/`UNREVIEWED`).
  2. A signed-off remediation plan for any finding that will not be baselined.
  3. A change ticket flipping `SECURITY_ENFORCEMENT_MODE` to `enforce`.

**Until that cutover, the pipeline is report-only by design. This is a temporary
state, not a permanent control weakness, and the cutover date is a tracked
commitment.**

<a id="3-the-security-baseline-how-exceptions-work"></a>

## 3. The security baseline — how exceptions work

`.security-baseline.json` is the risk-acceptance ledger. Each entry is a
fingerprint of `(rule, file, normalised offending code)` so it survives line
shifts but is invalidated when the code actually changes.

An entry is **accepted** only when all three are present:
- `owner` — accountable person/team (not `UNASSIGNED`)
- `justification` — why it is safe as-is
- `expires` — a date; expired entries are **re-raised** automatically

Entries generated by `ci-security-check.ps1 -UpdateBaseline` ship with
placeholder values and are treated as **invalid** (i.e. not accepted). They are
re-raised as active findings the moment the gate moves to `enforce`. Do **not**
commit `-UpdateBaseline` output as if it were approved sign-off.

Regenerate after a legitimate fix: `pwsh -File scripts/ci-security-check.ps1
-UpdateBaseline`, then set owner/justification/expiry on the remaining entries.

<a id="6-retention"></a>

## 6. Retention

GitLab artifact `expire_in` values in this pipeline are set to 1 year (security
evidence) / never (compliance record copy). These are convenience copies. EMIR
Art. 39 requires records for at least five years; the **authoritative** archive
is the Bank's evidence store, populated from `compliance-evidence` output on a
nightly export. Do not rely on GitLab artifact retention alone.
